# Spec למימוש — מרקטפלייס להתאמת מפתחים (בנייה מאפס)

מסמך מימוש ל-CC. הרעיון: לקוח שרוצה שיבנו לו פרויקט מאפס (אתר, אפליקציה, אוטומציה, בוט, SaaS) עונה על 5 שאלות ומקבל רשימה קצרה וממוקדת של מפתחים ישראלים שמתאימים למה שהוא צריך — כל אחד עם ציון התאמה, מודל תמחור, ופנייה ישירה בוואטסאפ. אין צ'אט פנימי, אין תיווך. הלקוח מדבר עם המפתח ישירות.

ההתאמה כולה rule-based ודטרמיניסטית — אותה פנייה מחזירה תמיד אותה תוצאה. בלי LLM בלב המערכת. הכל רץ ב-query אחד ל-Supabase + חישוב בזיכרון.

---

## 0. כללי עבודה ל-CC

לפני קוד — plan. לא לכתוב מימוש לפני שהוצגה תוכנית והוסכמה. תמיד plan mode.
פתרונות שורש, לא טלאים — כשיש באג, לרדת ל-root-cause ולא לעטוף בתיקון נקודתי.
Stack קיים: FastAPI על Render, Supabase (PostgreSQL), פרונט קיים. אין LLM בליבת ההתאמה.

## 1. העיקרון המרכזי — סוג הפרויקט הוא הציר

סוג הפרויקט הוא הדבר שבאמת קובע אם ההתאמה טובה. בבנייה מאפס, ללקוח לרוב לא אכפת אם המפתח עובד ב-Cursor או Windsurf — אכפת לו אם המפתח בונה את הדבר שהוא צריך. מי שבונה אתרי תדמית הוא לא בהכרח מי שבונה בוטים קוליים, וזה ההבדל שמכריע.

עשר קטגוריות סוג-פרויקט. הלקוח בוחר אחת, המפתח מסמן כמה שרוצה (בלי תקרה):

`landing` אתר תדמית · `store` חנות אונליין · `mobile` אפליקציית מובייל · `webapp` Web App · `saas` מערכת SaaS · `automation` אוטומציה ואינטגרציות · `bot_chat` בוט (WhatsApp/Telegram) · `bot_voice` בוט קולי · `ai_agents` AI ואייג'נטים · `other` אחר

**הכרעה: אין חפיפה חלקית.** התאמת סוג פרויקט היא בינארית — או שהמפתח סימן בדיוק את הקטגוריה שהלקוח בחר, או שאין התאמה על הגורם הזה. `webapp` ו-`saas` נחשבים נפרדים לגמרי, וכך גם `bot_chat` ו-`bot_voice`. **המשמעות:** לקוח שבוחר "לא נכון" בין webapp ל-saas לא יראה מפתחים מהצד השני. מפצים על זה ב-UI — תיאור ברור ליד כל קטגוריה שיעזור ללקוח לבחור נכון. למשל: "Web App — מערכת עם משתמשים והתחברות; SaaS — מערכת עם מנוי ותשלום חוזר".

## 2. סכמת Supabase

ארבע טבלאות. `developers` ו-`requests` הן הלב; `referrals` היא logging ובסיס ל-reputation עתידי; `project_types` היא lookup אופציונלי.

### 2.1 `developers`

| שדה | טיפוס | הערות |
|---|---|---|
| `id` | `uuid` PK | `default gen_random_uuid()` |
| `full_name` | `text` NOT NULL | |
| `title` | `text` | תפקיד חופשי — "Full-stack, ייעוץ" |
| `bio` | `text` | תיאור כללי — עד ~280 תווים |
| `highlight` | `text` | **חדש.** "במה אני טוב במיוחד" — משפט בידול קצר. משלים את ה-bio הכללי במשהו חד |
| `avatar_url` | `text` | תמונת פרופיל. יש upload flow (ראה 2.5) |
| `whatsapp_e164` | `text` NOT NULL | E.164 בלבד: `972501234567`. **לא מוצג בפומבי** (ראה RLS) |
| `project_types` | `text[]` NOT NULL | מתוך 10 הקטגוריות. **בלי תקרה** |
| `stack` | `text[]` | טכנולוגיות. חצי-פתוח — רשימה מנוהלת + "אחר". **נכנס למנוע במשקל מלא** |
| `ai_tools` | `text[]` | כלי AI. **תצוגה בלבד — לא נכנס למנוע** |
| `pricing_models` | `text[]` NOT NULL | **חדש, מחליף price_min/max.** מערך מתוך: `hourly` / `after_scoping` / `budget_friendly`. multi |
| `hourly_rate` | `integer` | סכום ₪ לשעה. מופיע ורלוונטי **רק אם** `pricing_models` כולל `hourly`. **תצוגה בלבד — לא נכנס למנוע** |
| `availability` | `text` NOT NULL | enum: `available` / `limited` / `unavailable` |
| `portfolio_url` | `text` | **קריטי בבנייה מאפס.** בסיס לפילטר "רק עם תיק עבודות" |
| `links` | `jsonb` | `{"linkedin": "...", "github": "..."}` |
| `is_verified` | `boolean` NOT NULL default `false` | badge "מאומת". שובר-שוויון במנוע |
| `is_active` | `boolean` NOT NULL default `true` | השהיה עצמית בלי מחיקה |
| `created_at` | `timestamptz` default `now()` | |
| `updated_at` | `timestamptz` default `now()` | trigger. שובר-שוויון במנוע |

הערה על `pricing_models` ו-`hourly_rate`: מודל התמחור והמחיר אוחדו לשדה גמיש אחד במקום טווח קשיח. מפתח יכול לסמן כמה מודלים — טיפוסי: `["hourly", "budget_friendly"]` עם `hourly_rate: 350`. מפתח אחר: `["after_scoping"]` בלי מספר כלל. ה-`hourly_rate` הוא **מידע תצוגה ללקוח** על הכרטיס, לא קריטריון סינון — הלקוח רואה "350 ₪ לשעה" ומחליט בעצמו.

`budget_friendly` הוא tag משותף: הלקוח מסמן אותו בשאלות, המפתח מסמן אותו בפרופיל, והמנוע מתאים בחפיפה רגילה. אין הצלבה מול המחיר — מפתח שמסמן `budget_friendly` ומקליד `hourly_rate` גבוה לא נחסם (הכרעה: gaming רמה 1, תיקון עצמי — הפנייה הישירה לוואטסאפ חושפת אי-התאמה מיד).

**החלטת ארכיטקטורה — `project_types` כמערך על השורה, לא טבלת join.** Postgres מטפל ב-`text[]` עם GIN index מצוין, השאילתות פשוטות, וההתאמה בקוד ולא ב-SQL join. אם אי פעם צריך metadata לכל שיוך — מנרמלים אז. אינדקסים: GIN על `project_types`, `stack`. B-tree על `availability`, `is_active`, `portfolio_url` (לפילטר תיק-עבודות).

### 2.2 `requests`

כל שורה היא פנייה של לקוח — התשובות שלו. גם טבלת analytics: כל חיפוש נשמר, גם בלי פנייה.

| שדה | טיפוס | הערות |
|---|---|---|
| `id` | `uuid` PK | |
| `project_type` | `text` NOT NULL | הבחירה המרכזית |
| `pricing_prefs` | `text[]` | multi: `hourly` / `after_scoping` / `budget_friendly`. רק `budget_friendly` נכנס למנוע |
| `timeline` | `text` | `urgent` / `weeks` / `flexible` |
| `involvement` | `text` | `full_handoff` / `collaborative`. **מטא-דאטה לפנייה — לא נכנס למנוע** |
| `portfolio_only` | `boolean` default `false` | **פילטר הלקוח** — הצג רק מפתחים עם `portfolio_url` |
| `description` | `text` | תיאור חופשי קצר. משמש לניסוח הפנייה, לא את המנוע |
| `matched_dev_ids` | `uuid[]` | מי הוחזר — ל-analytics |
| `created_at` | `timestamptz` default `now()` | |

**החלטת ארכיטקטורה — שומרים את הפנייה לפני שמראים תוצאות.** זה נותן analytics על ביקוש מול היצע — "40% בחרו saas ואין מספיק מפתחי saas" — תובנה שאי אפשר לקבל אם שומרים רק פניות מוצלחות. עלות: שורה זולה לכל חיפוש.

### 2.3 `referrals`

כל לחיצה על "פנה בוואטסאפ". analytics עכשיו, bootstrap ל-reputation אחר כך.

| שדה | טיפוס | הערות |
|---|---|---|
| `id` | `uuid` PK | |
| `request_id` | `uuid` FK → requests | |
| `developer_id` | `uuid` FK → developers | |
| `match_score` | `integer` | הציון שהוצג באותו רגע |
| `created_at` | `timestamptz` default `now()` | |

one-to-many: לקוח אחד יכול לפנות לכמה מפתחים מאותה תוצאה. שדות עתידיים אפשריים: `status`, `client_rating`.

### 2.4 `project_types` (lookup, אופציונלי)

`code` · `label_he` · `description_he` (לתיאור ה-UI ליד כל קטגוריה) · `sort_order` · `is_active`. מאפשר לשנות טקסט קטגוריה בלי deploy. אפשר להתחיל קשיח אם מעדיפים.

### 2.5 upload תמונת פרופיל

Supabase Storage — bucket ציבורי לקריאה (`avatars`). המפתח מעלה בהרשמה/עריכה, מקבל URL, נשמר ב-`avatar_url`. ולידציה: סוג תמונה, גודל מקסימלי סביר.

### RLS — קריטי

**`whatsapp_e164` לעולם לא יוצא ל-client דרך anon key.** הפרטיות היא feature מוצהר. מימוש: read ציבורי לטבלה **בלי העמודה הזו** (view שלא כולל אותה, או column-level policy). המספר נחשף אך ורק דרך `POST /referrals`, שגם רושם את הפנייה. כך הפרטיות והלוגינג נאכפים באותו choke point, ואי אפשר לדלוף מספר בלי שהוא נרשם.

## 3. מנוע ההתאמה

הלב, ומה שמפריד מקבוצת וואטסאפ. דטרמיניסטי, זול, ניתן לדיבוג.

### 3.1 סינון מקדים (pre-filter)

לפני ניקוד, מסננים החוצה מי שלא רלוונטי:

- `is_active = true` וגם `availability != 'unavailable'`.
- **התאמת סוג פרויקט מדויקת:** `project_type` של הלקוח נמצא ב-`project_types` של המפתח. אין חפיפה חלקית — מי שלא סימן בדיוק את הקטגוריה, יוצא.
- **אם `portfolio_only = true`:** רק מפתחים עם `portfolio_url` לא-ריק.

מי שעבר — עובר לניקוד.

### 3.2 הנוסחה

שלושה גורמים (services ירד; חפיפה חלקית ירדה; המשקל של סוג-פרויקט ו-stack עלה בהתאם). כל הניקוד במספרים מדויקים:

| גורם | משקל מקס' | חישוב |
|---|---|---|
| התאמת סוג פרויקט | 50 | המפתח עבר את הסינון = התאמה מדויקת = מלוא 50. (אין חלקי — מי שלא התאים כבר סונן) |
| התאמת stack | 30 | לפי חפיפת `stack_pref` הלקוח מול `stack` המפתח — פירוט למטה |
| זמינות + לו"ז | 20 | לפי `availability` ו-`timeline` — טבלה למטה |

בונוס נפרד (לא חלק מ-100 הבסיס): **`budget_friendly` match = +10.** אם הלקוח סימן `budget_friendly` וגם המפתח סימן אותו → +10 לציון. אחרת 0. זה דוחף מפתחים נגישים למעלה כשהלקוח ביקש, בלי לפסול אף אחד.

הציון הסופי מנורמל ל-0–100 לתצוגה ("94% מתאים").

**חישוב `stack` (30):**
- הלקוח לא ציין `stack_pref` (רוב המקרים — לקוחות לא-טכניים) → הגורם לא פעיל, 30 הנקודות מתחלקות פרופורציונלית לשני הגורמים האחרים (סוג פרויקט וזמינות עולים יחסית). כך לקוח לא-טכני לא נענש, וההתאמה נשענת על מה שחשוב לו.
- הלקוח ציין `stack_pref` → ציון לפי חפיפה: כמה מהטכנולוגיות שהלקוח ביקש נמצאות ב-`stack` של המפתח, יחסית למספר שביקש. חפיפה מלאה = 30, חלקית = יחסי, אפס חפיפה = 0 (אבל המפתח לא נפסל — עדיין יכול להופיע אם ציונו הכולל גבוה).

הערה: `stack` נכנס במשקל מלא (לא רק אם צוין) — הכרעת המשתמש, כי הרבה פרויקטים דורשים stack ספציפי (React Native מול web). המנגנון: אם הלקוח כן ציין, זה גורם משמעותי (30); אם לא, מתחלק.

**חישוב זמינות + לו"ז (20):**

| מצב | ניקוד |
|---|---|
| `available` + לקוח `urgent` | 20 |
| `available` + לקוח `weeks`/`flexible` | 18 |
| `limited` + לקוח `flexible` | 14 |
| `limited` + לקוח `weeks` | 10 |
| `limited` + לקוח `urgent` | 5 |

(`unavailable` כבר סונן ב-pre-filter.)

### 3.3 tie-breaking והחזרה

מחזירים top-5 עד top-8 (קצר וממוקד עדיף על ארוך). שוברי שוויון בציון זהה, לפי הסדר: `is_verified` קודם → `availability = available` קודם → `updated_at` עדכני יותר.

**רשת ביטחון במקום anti-gaming:** אין תקרה על סוגי פרויקט (הכרעת המשתמש — רוב המפתחים נצמדים למה שהם באמת בונים). ה-tie-breaking הוא ההגנה: אם מפתח יסמן הכל, הוא יופיע בהרבה חיפושים אבל יצנח מתחת למי שאומת ופעיל. אם analytics יראו שמפתח בודד מופיע בכל חיפוש (דרך `matched_dev_ids` + `referrals`) — לשקול דילול/תקרה אז, על סמך נתונים.

אם אף מפתח לא עבר את הסינון → מסך ריק עם הפניה לפרסום בקשה פתוחה, לא תוצאות מזויפות.

## 4. ה-Flows

### 4.1 flow המפתח — הרשמה

מסך אחד, מחולק לקטעים. auto-publish: ברגע ששלח, הפרופיל חי וניתן להתאמה, `is_verified=false`. אין אישור ידני שחוסם.

הקטעים: פרטים בסיסיים (שם, תפקיד, bio, **highlight**, **avatar upload**) → **סוגי פרויקט** (בחירה מ-10, בלי תקרה — ה-UI מדגיש שזו ההתמחות שלפיה ימצאו אותו) → stack (חצי-פתוח, "אחר") → כלי AI (משני) → **מודל תמחור** (multi: hourly + שדה `hourly_rate` / after_scoping / budget_friendly) → זמינות → **פורטפוליו** (מודגש — בלי זה לקוחות עם פילטר תיק-עבודות לא יראו אותו) → קישורים → וואטסאפ (עם הבהרה: לא מוצג בפומבי, נחשף רק בפנייה).

**החלטת ארכיטקטורה — auto-publish עם `is_verified`.** אישור ידני הופך אותך לצוואר בקבוק, המוצר לא עובד בזמן שאתה ישן, והמפתח הראשון שמחכה יומיים עוזב. כולם עולים מיד; badge "מאומת" נוסף בקצב שלך.

### 4.2 flow הלקוח — מהשאלות לפנייה

הלקוח נוחת, לוחץ "מצא מפתח", ועונה על 5 שאלות. **בלי הרשמה ובלי פרטים מראש** — קודם רואים ערך, אחר כך כל החלטה.

השאלות (הסדר משקף חשיבות):
1. **מה לבנות?** — 10 הקטגוריות (עם תיאור ליד כל אחת, כי אין חפיפה חלקית). single-select.
2. **תמחור** — `hourly` / `after_scoping` / `budget_friendly`. **multi-select** (לא סותרים). רק `budget_friendly` נכנס למנוע.
3. **לו"ז** — `urgent` / `weeks` / `flexible`. single.
4. **רמת מעורבות** — `full_handoff` / `collaborative`. single. **מטא-דאטה לפנייה — לא במנוע.**
5. **תיאור קצר** — טקסט חופשי, אופציונלי.

פלוס: **toggle "הצג רק מפתחים עם תיק עבודות"** (`portfolio_only`).

**חשוב על ה-UI:** השאלות הן מסך flow ייעודי במוצר, **לא רכיב שאלון בתוך צ'אט.**

הלקוח שולח → נשמרת שורת `requests` → המנוע רץ → מסך תוצאות: top-5–8, כל כרטיס עם שם, תפקיד, highlight, bio, ציון התאמה, מודל תמחור (+`hourly_rate` אם יש), זמינות, לינק פורטפוליו, כפתור "פנה בוואטסאפ".

לחיצה על "פנה" → `POST /referrals` → נרשמת שורה, נחשף המספר, נפתח `wa.me/972...` עם הודעה מוכנה (כוללת את `description` ו-`involvement` כהקשר: "מחפש מפתח לבניית X, מעדיף עבודה שיתופית"). **זה הרגע היחיד שהמספר נחשף.**

**החלטת ארכיטקטורה — wa.me deep-link, בלי צ'אט פנימי.** שני הצדדים כבר על וואטסאפ, זה הכלי שבו עסקים ישראלים מתקשרים. צ'אט פנימי מוסיף עומס תחזוקה עצום (notifications, spam, moderation) בלי ערך. ה-deep-link מכניס אותם לערוץ שהם כבר משתמשים בו; השכבה היחידה שמוסיפים היא logging.

## 5. API Endpoints

Backend דק. ההיגיון המורכב היחיד הוא המנוע, שרץ ב-endpoint אחד.

| Method | Path | תיאור |
|---|---|---|
| `POST` | `/developers` | הרשמת מפתח. ולידציה: E.164, enum זמינות, `pricing_models` תקין, `hourly_rate` רק אם hourly |
| `GET` | `/developers/:id` | פרופיל ציבורי — **בלי `whatsapp_e164`** |
| `PATCH` | `/developers/:id` | עדכון (כולל השהיה עצמית דרך `is_active`) |
| `POST` | `/avatars` | upload תמונת פרופיל → מחזיר URL |
| `GET` | `/meta/project-types` | רשימת סוגי פרויקט + תיאורים (מ-lookup) |
| `POST` | `/match` | **הלב.** מקבל תשובות הלקוח, שומר `requests`, מריץ מנוע, מחזיר top-N (בלי מספרים) |
| `POST` | `/referrals` | רושם פנייה, **מחזיר מספר וואטסאפ**. הנקודה היחידה שהמספר יוצא |

### 5.1 `POST /match` — schema

Request:
```
{
  "project_type": "saas",
  "pricing_prefs": ["hourly", "budget_friendly"],
  "timeline": "weeks",
  "involvement": "collaborative",
  "portfolio_only": true,
  "description": "מערכת ניהול לקוחות עם דשבורד",
  "stack_pref": ["React", "Supabase"]
}
```
(`stack_pref`, `pricing_prefs`, `description` אופציונליים. `project_type`, `timeline` חובה.)

Response:
```
{
  "request_id": "uuid",
  "results": [
    {
      "developer_id": "uuid",
      "full_name": "...",
      "title": "...",
      "highlight": "...",
      "bio": "...",
      "avatar_url": "...",
      "project_types": ["saas", "webapp"],
      "stack": ["React", "FastAPI", "Supabase"],
      "ai_tools": ["Claude Code", "Cursor"],
      "pricing_models": ["hourly", "budget_friendly"],
      "hourly_rate": 350,
      "availability": "available",
      "portfolio_url": "...",
      "links": {"linkedin": "...", "github": "..."},
      "is_verified": true,
      "match_score": 94
    }
  ]
}
```
**אין `whatsapp_e164` ב-response.** שגיאה: `422` על ולידציה, `200` עם `results: []` אם אין התאמות (לא שגיאה — מסך ריק עם הפניה לבקשה פתוחה).

### 5.2 `POST /referrals` — schema

Request: `{ "request_id": "uuid", "developer_id": "uuid" }`
Response: `{ "whatsapp_e164": "972501234567", "wa_link": "https://wa.me/972501234567?text=..." }`
(השרת בונה את ה-`wa_link` עם הודעה מוכנה מ-`description` + `involvement` של ה-request.)

זה ה-choke point של הפרטיות — **הדרך היחידה במערכת לקבל מספר.** אין endpoint אחר שמחזיר אותו, RLS חוסם גישה ישירה. אי אפשר לפנות בלי שהפנייה נרשמת.

## 6. מכוון ל-v2 (מתוכנן, לא בונים עכשיו)

הסכמה תומכת בכל אלה בלי migration כואב:

**Reputation כגורם דירוג.** `referrals` אוגר מהיום כמה פניות כל מפתח מקבל ובאיזה ציון. כשיהיו נתונים — מכפיל על ציון ההתאמה. הבסיס נאסף.

**anti-gaming לפי צורך.** אם analytics יראו מפתח שמופיע בכל חיפוש — דילול (ציון סוג-פרויקט נחלש ככל שמסמנים יותר סוגים) או תקרה. מחליטים על סמך נתונים, לא השערה.

**Analytics ביקוש↔היצע.** כל `requests` נשמר כולל חיפושים בלי פנייה. שאילתה תראה איפה הביקוש עולה על ההיצע — סיגנל להיכן להביא מפתחים.

**Verified badge בפעולה.** `is_verified` בטבלה; צריך UI ל-badge וממשק אדמין לסימון.
